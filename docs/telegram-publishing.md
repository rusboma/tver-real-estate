Работают новый серверный API и интерфейс, миграция manual_telegram_delivery уже установлена в Supabase. Проверка платформы не выявила frontend/backend/network errors. ## Путь публикации

1. Владелец создаёт бота через BotFather и добавляет его администратором с правом публикации в основной и отдельный тестовый канал.
2. Через одну защищённую форму AppDeploy вводятся TELEGRAM_BOT_TOKEN, TELEGRAM_CHANNEL_ID, TELEGRAM_TEST_CHANNEL_ID. Не вводить значения в чат, репозиторий, URL приложения или frontend. Каналы задаются @username либо числовым ID. Токен читает только сервер.
3. Кнопка «Проверить подключение» вызывает getMe/getChat/getChatMember, проверяет тип канала и право публикации, не отправляет сообщений. Каналы должны иметь разные числовые ID.
4. Редактор выбирает одобренный материал, открывает предпросмотр для тестового канала и подтверждает отправку. Тестовый пост сохраняется в журнале, не создаёт основную публикацию и не меняет статус статьи.
5. Успешный тест этим ботом для настроенного основного канала открывает основную ручную отправку. Перед ней есть отдельный предпросмотр с каналом, версией текста и подтверждением редактора.
6. Основная публикация отправляется сейчас независимо от времени плана. После подтверждённого ответа Telegram сохраняются message_id, время и статус published. Расписание не исполняется автоматически.

## Контент и безопасность

Текст и изображение берутся сервером из одобренного черновика и сохранённого источника, не из клиентского payload. Предпросмотр привязан к версии, отпечатку источника, плану, боту, числовому ID канала и последней попытке. При отправке всё проверяется заново. Истёкшие анонсы и неразрешённые дубли блокируются.

HTML экранируется. Заголовок выделяется жирным, ссылка на источник добавляется отдельно; рекламные призывы не добавляются. Лимит текста — 4096 знаков, с фото — 1024; используется консервативный подсчёт UTF-16. Текст не обрезается и не делится на несколько сообщений автоматически. Фото прикрепляется только по выбору редактора при наличии URL и проверке прав на его использование. Превью внешних ссылок для текстовых постов отключено.

Перед внешним запросом атомарно создаётся долговечная запись sending и резервируется основная публикация. Параллельная отправка одного материала запрещена частичными уникальными индексами. Внешний sendMessage/sendPhoto выполняется ровно один раз на попытку. При явном отказе Telegram (например 429) сохраняется failed и retry_after; повтор требует нового предпросмотра. При сетевой ошибке, серверном 5xx, неожиданном ответе, потере подтверждения записи или прерывании процесса результат считается неизвестным. Повторная отправка блокируется; срок ожидания автоматически не снимает блокировку.

Неизвестный результат требует сверки канала оператором. Если пост найден, после проверки message_id и target_chat_id можно завершить существующую попытку как sent через закрытый RPC. Кнопки автоматического разблокирования нет; unknown нельзя перевести в failed для слепого повтора. Если процесс остановился на sending, журнал после минуты предлагает проверить канал. Обработка неизвестных результатов — сознательное ограничение первой версии, защищающее от дублей.

Все API требуют AppDeploy Auth и разрешённый email администратора. Таблица telegram_deliveries закрыта RLS и отзывом прав anon/authenticated. RPC — security invoker, EXECUTE только service_role. Токены и сырые ответы ошибок Telegram не выводятся в браузер или журнал.

## Проверка и развёртывание

Пройдены 50 Node-тестов проекта, включая форматирование, лимиты, ошибки, права бота, единственный внешний вызов и потерю подтверждения. SQL-регрессия `test/telegram-publishing.sql` выполнена от роли service_role с rollback: без одобрения нельзя отправить; без теста запрещена основная публикация; устаревший preview не принимается; повтор/unknown/отмена активной отправки блокируются; успешная запись идемпотентна. Существующая SQL-регрессия публикационного плана также пройдена. Локальная проверка TypeScript новых файлов, их интеграции с backend/index.ts и текущими backend-зависимостями пройдена с React types и SDK-декларациями из справочника; AppDeploy-сборка и проверка запуска завершены 28 октября; полная авторизованная проверка отправки требует настройки бота. В tests/tests.json сохранены 12 прежних сценариев и добавлены 2 сценария Telegram; только ошибки 400–599 инъецируются через QA Faults. Платформа выдала рекомендательное предупреждение о числе тестов (14); прежние проверки сохранены для регрессии. Реальные сообщения при разработке не отправлялись.

Схема применена миграцией manual_telegram_delivery. Проверены закрытые права RPC и таблицы. Security Advisor показывает только INFO «RLS Enabled No Policy» для закрытых серверных таблиц; доступ клиента намеренно запрещён.

Перед развёртыванием прочитать AppDeploy get_deploy_instructions и src_read последних версий изменяемых файлов. `appdeploy/pending-telegram.json` фиксирует базовую и установленную версии; каталог содержит изменённые файлы, а не копию всего приложения. Если база изменилась, объединить изменения, не перезаписывая новые правки. Сначала выполнить сборку/проверку типов, затем deploy и QA. После настройки секретов проверить весь путь на одном согласованном материале в тестовом канале; основной пост редактор подтверждает отдельно.

Публикацию по расписанию подключать отдельным следующим этапом после успешной ручной проверки. Текущий Render scout не вызывает Telegram и не изменён.
